# tokensave 5.0 — Design & Implementation Plan

Companion to `docs/5.0-RELEASE-PLAN.md`. The release plan is the *what*; this is the *how*.

Three workstreams:

- **A.** Eight new MCP tools targeting measured Bash : tokensave gaps
- **B.** `tokensave_read` (mode-aware) plus a session response cache
- **C.** LSP-resolved cross-file edges (Phase 1 + 2)

Embeddings / RRF hybrid search is out of scope for 5.0 and not covered here.

---

## 1. Schema migration v7 → v8

A single bundled migration. Forward-only. Existing migration helpers in `src/db/migrations.rs` (see `migrate_v7` for the model).

```sql
-- Workstream C: LSP edge provenance
ALTER TABLE edges ADD COLUMN resolved_by TEXT NOT NULL DEFAULT 'direct';
CREATE INDEX idx_edges_resolved_by ON edges(resolved_by);

-- Workstream B: session response cache
CREATE TABLE read_cache (
    project_id   TEXT NOT NULL,
    session_id   TEXT NOT NULL,
    file_path    TEXT NOT NULL,
    mtime_ns     INTEGER NOT NULL,
    mode         TEXT NOT NULL,
    args_hash    TEXT NOT NULL,
    digest       TEXT NOT NULL,
    body         BLOB NOT NULL,
    token_count  INTEGER NOT NULL,
    created_at   INTEGER NOT NULL,
    PRIMARY KEY (project_id, session_id, file_path, mode, args_hash)
);
CREATE INDEX idx_read_cache_session ON read_cache(session_id, created_at);

-- Workstream A: new node kinds
-- StructLiteral and FieldAccess are new node-kind values; no schema change
-- needed (the `kind` column is TEXT). Migration adds two new edge kinds:
--   'instantiates'  StructLiteral -> Struct
--   'reads_field'   Function/Block -> Struct.Field
--   'writes_field'  Function/Block -> Struct.Field
-- Materialized lazily during sync; no backfill required for v8.
```

Test: extend `tests/migration_test.rs` with a v7 → v8 case asserting the new column defaults to `'direct'` for prior-version edges and that the `read_cache` table exists.

## 2. Workstream B — `tokensave_read` + response cache

The single most disruptive 5.0 change. Built first because four other tools (`outline`, `diagnostics`, `signature_search`, `field_sites`) reuse its cache layer.

### 2.1 Tool surface

```json
{
  "name": "tokensave_read",
  "input": {
    "file": "src/sync.rs",
    "mode": "auto | full | map | signatures | diff | lines | entropy",
    "lines": "120-180",
    "since": "HEAD~1",
    "limit": 4000
  }
}
```

Defaults: `mode = "auto"`, `limit = 4000` tokens. Anything that would exceed `limit` returns a header + truncation marker plus a hint to narrow `mode` or `lines`.

Modes:

| Mode | Source | Cost |
|---|---|---|
| `full` | raw file content | proportional to file |
| `map` | `nodes` rows for `file` sorted by `start_line` | one indexed query |
| `signatures` | `nodes` filtered to `kind in (Function, Method, Struct, Trait, Enum, Class)` with `signature` column | one indexed query |
| `lines` | byte-range slice of the file with surrounding symbol context | one indexed query + slice |
| `diff` | `git diff --no-color --unified=3 <since>..HEAD -- <file>` filtered to changed regions | one git invocation |
| `entropy` | full file with run-length compression of repeated whitespace, comment-block elision past N lines, import-block collapse | linear scan |
| `auto` | deterministic policy: `lines` if `lines` arg present; else `signatures` if file > 800 LOC; else `map` if > 200 LOC; else `full` | depends on chosen mode |

Response always includes `chosen_mode`, `digest` (SHA-256 of body), `token_count`, and `mtime_ns`. The `chosen_mode` field lets agents see what `auto` picked.

### 2.2 Response cache

Keyed by `(project_id, session_id, file_path, mode, args_hash)` where `args_hash = sha256(canonical_json({lines, since, limit}))`.

- `session_id` derives from the MCP transport. For stdio, the connect-time random ID. For HTTP (future), the bearer / session header.
- On hit with matching `mtime_ns`: response body becomes a 30-token stub:
  ```
  {"unchanged": true, "digest": "<sha>", "mtime_ns": <n>, "mode": "<m>", "token_count": <prior>}
  ```
- On miss or `mtime_ns` mismatch: compute, insert, return full body.
- `map` and `signatures` modes invalidate on graph snapshot change instead of (in addition to) file mtime — tracked by the existing `metadata.last_sync_at`.
- TTL: rows expire when their `session_id` exits. A session-end hook (`hook_stop`) drops them. As a safety net, sweep rows older than 24h on every connect.

The `body` column is gzip-compressed when > 1 KiB. The cache is per-project; nothing crosses project boundaries.

### 2.3 File touchpoints

```
src/mcp/tools/definitions.rs   def_read (~30 lines)
src/mcp/tools/handlers.rs      handle_read (~120 lines, dispatches by mode)
src/context/read_modes.rs      NEW. one fn per mode (~250 lines total)
src/context/read_cache.rs      NEW. CRUD + sweep (~150 lines)
src/db/migrations.rs           migrate_v8 (~40 lines)
tests/read_modes_test.rs       NEW. one test per mode + cache hit/miss (~200 lines)
```

Estimated total: ~800 lines, ~3 days.

### 2.4 Risks

- `git diff` on huge changesets blows past `limit`. Mitigation: clamp diff output to first `limit` tokens, mark truncation.
- `entropy` mode is heuristic; first cut elides only `/* */` blocks > 20 lines and consecutive blank lines. Tune later.
- Cache invalidation mismatch if files are edited externally during a session. Mitigation: on a `mtime_ns` mismatch, evict the row and recompute — never serve stale.

## 3. Workstream A — eight MCP tools

Order matches the build-order in `MCP-extensions.md`. Each entry: tool surface, where it lives, what it touches.

### 3.1 `tokensave_outline` (very low complexity, half-day)

`{ "file": "src/sync.rs", "kinds": ["function", "struct", "impl"] }`

Returns: flat array of `{kind, name, line, end_line, visibility}`. Sorted by `line`. No bodies. `kinds` filter optional; defaults to all top-level symbols.

Implementation: one query against the `nodes` table joined to `files`. ~80 lines in `handlers.rs`. Reuses `tokensave_module_api`'s formatter as a starting point but drops the public-only filter.

Tests: 3 cases — Rust file, Markdown file, kinds filter.

### 3.2 `tokensave_unsafe_patterns` (low complexity, half-day)

`{ "kinds": ["unwrap", "expect", "panic", "todo", "unimplemented", "unsafe_block"], "path": "src/", "exclude_tests": true }`

Returns: per match `{kind, file, line, enclosing_symbol, snippet, in_test}`. AST-matched, not regex.

Implementation: extends `src/extraction/` per-language extractors to emit `UnsafeMarker` nodes alongside symbols, gated behind a node-kind filter at query time so the storage cost is amortized over all sync passes. Per-language patterns live in the existing extractor traits — ~30 lines per language for the five languages with `unwrap`-equivalent patterns (Rust, Go panic, Python `assert False`, JS `throw`, TS `throw`).

`in_test` flag: derived from path (`tests/`, `*_test.rs`, `__tests__/`) and from `cfg(test)` annotations on enclosing nodes (already extracted).

Tests: fixtures in `tests/fixtures/unsafe_patterns/` per language.

### 3.3 `tokensave_implementations` (low complexity, 1 day)

`{ "trait": "LanguageExtractor" }` or `{ "method": "extensions" }`.

Returns: for each implementing type, the type name, file, signature, and method body (or bodies). Method edges already exist in the graph — this is a query, not an extraction change.

Implementation: ~100 lines in `handlers.rs`. Reuses `tokensave_type_hierarchy`'s walker for the `trait` form; for the `method` form, an indexed scan on `kind = 'Method' AND name = ?`.

Tests: 4 cases — by trait, by method, no matches, multiple impls of same method on different types.

### 3.4 `tokensave_diagnostics` (high complexity, 3-4 days)

`{ "scope": "workspace | affected | package | file", "since": "HEAD~1", "name": "...", "path": "..." }`

Returns: structured `errors` and `warnings` arrays. Each entry: `file`, `line_start`, `line_end`, `code`, `message`, `enclosing_symbol`, `snippet`. The snippet field reuses Workstream B's read cache.

Implementation strategy:

- One driver per language, dispatched by project detection:
  - Rust: `cargo check --message-format=json`
  - TypeScript: `tsc --noEmit --pretty false`
  - Python: `pyright --outputjson`
- A driver returns a stream of typed `Diagnostic` rows. Common shape lives in `src/diagnostics/mod.rs`; per-language parsers in `src/diagnostics/{rust,ts,python}.rs`.
- Affected-set scoping: when `scope = "affected"`, run the existing `tokensave_affected` first, build the package / file list, then pass it as the cargo / tsc target. For Rust this means `cargo check -p <pkg>` per affected package.
- Result digest: SHA-256 of the sorted diagnostic list. Cached at `metadata.last_diagnostics_digest`. A re-run with no source changes returns the cached digest with `unchanged: true` and zero recompilation cost (still runs cargo, but cargo's own cache makes it sub-second).
- `enclosing_symbol`: looked up by `(file, line_start)` in the graph.

File touchpoints:

```
src/diagnostics/mod.rs         Driver trait + dispatch (~150 lines)
src/diagnostics/rust.rs        Cargo JSON parser (~250 lines)
src/diagnostics/typescript.rs  tsc parser (~200 lines)
src/diagnostics/python.rs      pyright parser (~150 lines)
src/mcp/tools/handlers.rs      handle_diagnostics (~100 lines)
src/mcp/tools/definitions.rs   def_diagnostics (~40 lines)
tests/diagnostics_test.rs      NEW (~300 lines, one fixture per language)
```

Estimated total: ~1,200 lines, ~3-4 days.

Risks:

- cargo on a cold project takes minutes; users will time out. Mitigation: drop the `default-target-dir` warning into the response on first call, advise daemon usage. Warm cargo runs are sub-second.
- TypeScript projects without `tsconfig.json` need a heuristic root-finder. Same pattern as the LSP TypeScript adapter.
- `cargo check` requires a writable target dir. Use the existing `.tokensave/target/` to avoid colliding with user builds.

### 3.5 `tokensave_signature_search` (medium complexity, 1-2 days)

`{ "returns": "Result<_, anyhow::Error>", "params": ["&mut self", "_"], "async": true, "attribute": "#[tokio::test]" }`

Returns: matching symbols with `file`, `line`, `signature`, `kind`, matched sub-pattern.

Implementation: ast-grep is already a dependency (`tokensave_ast_grep_rewrite`). Wrap its matcher in a query mode. Build an ast-grep pattern from the structured input per language. ~250 lines in `src/extraction/signature_match.rs`.

Skip Python and dynamic langs in the first cut; Rust + TS + Go cover the high-traffic refactor questions.

### 3.6 `tokensave_constructors` (medium complexity, 1-2 days, schema-extending)

`{ "struct": "GraphStats" }`

Returns: every struct-literal site with `file`, `line`, `field_list`, `missing_fields` (vs. the struct's current field set).

Implementation: extend the Rust + Go + TS extractors to emit `StructLiteral` nodes with `instantiates` edges to the target struct. Also emit a `field_list` JSON blob on each `StructLiteral` node. Migration v8 adds the new edge kind to the legal-kinds set; storage is unchanged.

`missing_fields` is computed at query time by diffing the literal's field list against the struct's `Contains Field` edges.

File touchpoints:

```
src/extraction/{rust,go,typescript}/*.rs   +30-50 lines per language
src/mcp/tools/handlers.rs                  handle_constructors (~80 lines)
tests/extractor_test.rs                    +3 cases (one per language)
```

### 3.7 `tokensave_field_sites` (medium complexity, 2-3 days, schema-extending)

`{ "field": "GraphStats::last_sync_at", "writes_only": false }`

Returns: `read_sites` and `write_sites` arrays, each entry `{file, line, enclosing_symbol, snippet}`.

Implementation: this is the largest schema-extending tool. Per-language extractors already walk function bodies for call edges; extend the walk to also emit `reads_field` and `writes_field` edges.

For Rust: tree-sitter `field_expression` matches a read; `assignment_expression` whose left side is a `field_expression` matches a write; `&mut` deref makes it a write conservatively. For TS: `member_expression` plus assignment context.

Detection accuracy goal: 95%+ on the tokensave repo's own field accesses (validate with a regression fixture). False positives on writes are the dangerous failure mode (you rename a field thinking only N writes exist, miss one). False negatives are merely annoying.

File touchpoints:

```
src/extraction/{rust,go,typescript,python}/*.rs   +60-100 lines per language
src/db/migrations.rs                              +new edge kind in v8
src/mcp/tools/handlers.rs                         handle_field_sites (~120 lines)
tests/field_sites_test.rs                         NEW (~200 lines)
```

Estimated: ~700 lines, 2-3 days.

### 3.8 `tokensave_config` (medium complexity, 1-2 days)

`{ "path": "Cargo.toml", "key": "package.version" }` or `{ "glob": "**/Cargo.toml", "key": "dependencies.tokio" }`

Returns: parsed value(s), `file`, `line` of the key.

Implementation: `toml` and `serde_yaml` crates (TOML already a dep). JSON pointer-style key paths with `[*]` for wildcards. ~200 lines in `src/mcp/tools/handlers.rs`.

No schema change. No graph involvement.

## 4. Workstream C — LSP integration

The detailed design is already in `docs/LSP-INTEGRATION.md` (architecture, adapter trait, edge provenance, configuration, performance, rollout). Implementation plan summary:

### 4.1 Phase 1 — standalone binaries

Target languages: Rust, Go, C/C++/Obj-C (clangd), Zig, Lua. Adapter binaries are pure-binary, no runtime dependency.

```
src/lsp/mod.rs                   LspManager (~300 lines)
src/lsp/client.rs                JSON-RPC transport (~400 lines)
src/lsp/protocol.rs              LSP message types (~300 lines)
src/lsp/resolver.rs              UnresolvedRef -> Edge bridge (~250 lines)
src/lsp/adapters/{rust,go,clangd,zig,lua}.rs   ~80 lines each
src/sync.rs                      Pipeline integration (~80 lines)
src/db/migrations.rs             resolved_by column in v8 (~30 lines)
src/config.rs / tokensave.toml   [lsp] section (~80 lines)
tests/lsp/                       Mock client + per-language fixtures (~600 lines)
```

Estimated: ~2,600 lines, ~1 week.

Pipeline integration in `src/sync.rs` is a single insertion between the extractor pass and the existing `ReferenceResolver::resolve_all()`. The LSP resolver accepts `&mut Vec<UnresolvedRef>`, drains the entries it can resolve into the edge buffer, and leaves the rest for the heuristic resolver.

### 4.2 Phase 2 — Node.js servers

Target: TypeScript, JavaScript, Python (pyright), PHP (intelephense). Gated on `node` being on `$PATH`.

```
src/lsp/node_detect.rs                            ~30 lines
src/lsp/adapters/{typescript,python,php}.rs       ~80 lines each
tests/lsp/node_*.rs                               ~300 lines
```

Estimated: ~600 lines, ~3 days.

### 4.3 Edge provenance

`Edge { resolved_by: Direct | Heuristic | Lsp }`. Migration v8 adds the column with `'direct'` default. Existing extractor code paths set `resolved_by = Direct` on emitted edges; the heuristic and LSP resolvers set `Heuristic` and `Lsp` respectively.

This unlocks two later capabilities not in 5.0 scope: (1) confidence-weighted impact analysis, (2) "show me edges that are heuristic-only" debug queries. Both are pure consumers of the column once it exists.

### 4.4 Configuration & kill switches

- `tokensave.toml` `[lsp]` section: `enabled` (default true), `timeout_secs`, `per_request_timeout_ms`, per-server `disable` flags
- `tokensave sync --no-lsp` / `--lsp-only`
- `TOKENSAVE_LSP=0` environment variable
- Doctor check: `tokensave doctor` reports detected LSP binaries and the per-language enabled status

## 5. Sequencing

The work decomposes into roughly four parallel-friendly threads. Order within each thread is forced by dependencies; threads themselves are mostly independent.

```
Thread 1 (Foundation):     v8 migration -> read_cache shell -> tokensave_read full+lines mode
Thread 2 (Quick MCP wins): outline -> unsafe_patterns -> implementations
Thread 3 (LSP):            client/protocol/manager -> Phase 1 adapters -> pipeline integration -> Phase 2
Thread 4 (Heavy MCP):      diagnostics (after Thread 1) -> constructors -> field_sites -> signature_search -> config
```

Recommended absolute order if a single contributor: run Thread 1 to completion first (everyone else benefits from the cache), then alternate between Thread 2 quick wins and Thread 3 LSP work, finishing with Thread 4 heavy items.

### 5.1 Milestone breakdown

- **5.0-alpha.1**: v8 migration + `tokensave_read` (full, lines, map). Three quick-win MCP tools. LSP client/protocol stubs but no adapters. Internal-only.
- **5.0-alpha.2**: LSP Phase 1 (Rust + Go adapters). `tokensave_diagnostics` for Rust. Read modes `signatures` and `diff`. First public alpha on the beta channel.
- **5.0-beta.1**: LSP Phase 1 complete (clangd, zls, lua-ls). `tokensave_diagnostics` adds tsc and pyright. `tokensave_constructors`.
- **5.0-beta.2**: LSP Phase 2 (TS, Python, PHP). `tokensave_field_sites`. `tokensave_signature_search`. `tokensave_config`.
- **5.0.0**: Stabilize, write upgrade notes, full doctor check coverage.

### 5.2 Cut points

If schedule slips, cuts in priority order:

1. LSP Phase 2 → 5.1 (Phase 1 covers the largest userbases)
2. `tokensave_field_sites` → 5.1 (largest schema-extending item)
3. `tokensave_constructors` → 5.1 (schema-extending; depends on field_sites' edge work for synergy)
4. Read modes `entropy` and `auto` → 5.1 (the explicit modes cover most needs; `auto` is convenience)

What does **not** cut: the v8 migration, Workstream B's `full`/`lines`/`map` modes, `outline`, `diagnostics`, and LSP Phase 1 — these define what makes 5.0 worth a major bump.

## 6. Testing strategy

- **Unit tests** colocated with each module, following the existing `tests/mcp_handler_test.rs` pattern.
- **Migration test** (`tests/migration_test.rs`): v7 → v8 round-trip plus assertion that the `resolved_by` default is applied.
- **Per-language fixtures** for Workstream A schema-extending tools live under `tests/fixtures/<feature>/<lang>/`. Mirror the existing `tests/fixtures/extractor/` layout.
- **LSP integration tests** require real LSP binaries. Gate behind `cfg(feature = "lsp-integration")` and run in CI on a Linux job that installs the Phase 1 servers (apt install + cargo install + manual binary fetch for zls and lua-ls).
- **Cache correctness test**: serial test that touches a file's mtime mid-session and verifies the cache row is evicted, not served stale.
- **Token-savings regression test**: a small fixture project with golden expected `token_count` values for each read mode. Catches regressions where a mode drifts in size.

## 8. Open questions

These need a call before kickoff:

1. **Read cache scope** — per-session vs. cross-session. Cross-session cache is more powerful but introduces correctness risk under external file edits. Recommendation: per-session for 5.0; revisit in 5.x with file-watch invalidation.
2. **`tokensave_diagnostics` cargo target dir** — sharing user's `target/` saves time but risks cache poisoning when the user has different feature flags active. Recommendation: use `.tokensave/target/` always; document the disk cost.
3. **LSP server installation** — should `tokensave install` offer to install rust-analyzer / gopls? Recommendation: no. Stay out of toolchain management; `tokensave doctor` reports what's missing.
4. **Field-write edge accuracy floor** — what false-positive / false-negative rate ships? Recommendation: 95% recall, 99% precision on writes, validated against the tokensave repo's own history. Lower precision is the risk; rather under-emit than over-emit.
