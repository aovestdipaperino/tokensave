# tokensave 5.0 — Release Plan

5.0 is the first major-version bump since the graph schema stabilized. It tightens the I/O surface (mode-aware reads, response caching), upgrades edge accuracy (LSP-resolved edges), and ships the highest-value MCP tools surfaced by the 2026-05-04 telemetry scan.

The unifying goal: cut the Bash : tokensave call ratio from ~23× toward parity by replacing recurring grep / Read / cargo loops with one structured tool call each.

---

## Workstreams

### A. MCP tool surface — highest-evidence gaps

Drawn from `docs/MCP-extensions.md` build-order. Ship in this order — each row addresses a distinct, measured class of recurring shell work.

| Tool | Evidence | Complexity | Notes |
|---|---|---|---|
| `tokensave_outline` | 618 symbol-skeleton greps | Very low | File → flat `{kind, name, line, visibility}` list. Reuses the graph; no extraction work. Ships first. |
| `tokensave_unsafe_patterns` | recurring in review/audit | Low | AST predicates (`unwrap`, `expect`, `panic!`, `todo!`, `unsafe`) over the existing matcher. `in_test` flag. |
| `tokensave_diagnostics` | 777 `cargo *` invocations | High | Wraps cargo / tsc / pyright. Returns structured errors mapped to graph nodes. Affected-set scoping via `tokensave_affected`. Biggest single Bash : tokensave gap. |
| `tokensave_implementations` | recurring trait-survey pattern | Low | All types implementing trait or method, with bodies. Method edges already present. |
| `tokensave_signature_search` | refactor question class | Medium | Search by return type / params / attributes. Reuses the `ast_grep_rewrite` matcher. |
| `tokensave_constructors` | struct-literal blast-radius | Low-Medium | Needs a struct-literal node kind in the schema. |
| `tokensave_field_sites` | field rename / invariant work | Medium | Read- vs. write-site partition. Requires field-level edges; schema audit needed. |
| `tokensave_config` | 62 TOML/YAML greps | Medium | TOML/YAML structured queries (`Cargo.toml`, workflows, `tsconfig.json`). |

`tokensave_lockfile_diff`, `tokensave_external_node`, `tokensave_macro_expand`, and `tokensave_feature_map` from the source doc are deferred past 5.0.

### B. Mode-aware read primitive + response cache (lean-ctx #1 + #5)

`tokensave_read(file, mode=...)` becomes the agent's drop-in for the raw `Read` tool.

Modes:

- `full` — verbatim file content (parity with raw Read)
- `map` — symbol outline served from the graph (cheap)
- `signatures` — function/type signatures only (cheap)
- `diff` — changed regions vs. last-call or vs. a git ref
- `lines:A-B` — explicit range (replaces 52 `sed -n` invocations from the scan)
- `entropy` — variable-density sampling for very large files
- `auto` — chooses `signatures | map | full` from request size and prior-call history

Response cache, keyed by `(file_path, mtime, mode, args)`:

- On a cache hit, return a small "unchanged since prior call this session" stub (target ≤ 30 tokens) plus a content digest.
- Invalidation is mtime-based for the file and graph-snapshot-based for symbol modes.
- The cache also addresses the heavy-re-read observation in `MCP-extensions.md` (76× / 85× / 47× Reads of the same file in single conversations).

Design notes:

- Single tool, not one per mode — fewer entries in the agent's tool catalog.
- `auto` mode emits a `chosen_mode` field in the response so the agent can learn the selection it would have made manually.
- The cache lives in the per-project `.tokensave/` DB; nothing leaves the machine.

### C. LSP-resolved edges

Per `docs/LSP-INTEGRATION.md`. Replaces the heuristic `ReferenceResolver` for cross-file edges when an LSP server is present, with graceful degradation when it isn't.

Phase 1 in 5.0 (ship-blocking):

- `src/lsp/` module: client, protocol, manager, resolver
- Adapters: `rust-analyzer`, `gopls`, `clangd` (C/C++/Obj-C), `zls`, `lua-language-server`
- Pipeline: LSP pass between extraction and the existing heuristic resolver; remainder falls through
- `Edge.resolved_by` provenance: `Direct | Heuristic | Lsp` (DB migration with default `'direct'`)
- Config: `tokensave.toml [lsp]` section, `--no-lsp` / `--lsp-only`, `TOKENSAVE_LSP=0`

Phase 2 in 5.0 if Phase 1 lands cleanly: `typescript-language-server`, `pyright-langserver`, `intelephense`. Phase 3 (daemon-kept servers) and Phase 4 (JVM / .NET / Swift) defer to 5.x.

Embedding-based hybrid search (was Workstream C) is **out of scope for 5.0** and deferred to a later release.

Sync-time impact is documented; mitigation via daemon-kept servers, parallel startup, selective `didOpen`, early termination.

## Schema & migrations

Single migration bundle for 5.0:

- `edges.resolved_by TEXT NOT NULL DEFAULT 'direct'` (Workstream C)
- `read_cache(file_path, mtime, mode, args_hash, body, digest, created_at)` (Workstream B)
- New node kinds / edges for `tokensave_constructors` and `tokensave_field_sites` (Workstream A)

All migrations are forward-only; the existing `migration_test` infrastructure covers v7 → v8.

## Sequencing

1. **Foundation** — schema migration, `tokensave_read` skeleton with `full` + `lines` modes, response cache shell.
2. **Quick wins** — `tokensave_outline`, `tokensave_unsafe_patterns`, `tokensave_implementations`. Cheap, high-ratio.
3. **LSP Phase 1** — Rust + Go + clangd + Zig + Lua. Validates the pipeline before broadening.
4. **Read modes** — `map`, `signatures`, `diff`, `auto`. Cache hit-rate telemetry.
5. **Diagnostics** — the largest single bash gap; build after read modes so error snippets reuse the cache.
6. **LSP Phase 2** — TypeScript + Python + PHP. Gated on Node.js detection.
7. **Schema-extending tools** — `tokensave_constructors`, `tokensave_field_sites`.
8. **Config / signature search** — `tokensave_config`, `tokensave_signature_search`.

Cuts to make 5.0 ship: defer LSP Phase 2 if Phase 1 surfaces stability issues. The remaining workstreams are orthogonal and can ship per-row.

---

## Compatibility

- All existing tool names and response shapes are preserved. New fields on existing tools are additive.
- Cargo feature tiers (`lite | medium | full`) are unchanged.
- `tokensave_read` does not deprecate any existing tool — `tokensave_node`, `tokensave_body`, and `tokensave_module_api` remain canonical for symbol-scoped queries.
- LSP is opt-out, never opt-in: an installed binary is treated as consent. `TOKENSAVE_LSP=0` is the kill switch.
